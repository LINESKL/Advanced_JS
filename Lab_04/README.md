# Lab 4 — Anti-Patterns & Refactoring

### Identifying and Fixing Anti-Patterns in JavaScript

</div>

## Описание

Лабораторная работа посвящена изучению антипаттернов в JavaScript-коде и методам рефакторинга legacy-кода. Включает практический анализ проблемного кода, идентификацию антипаттернов и их устранение с помощью паттернов проектирования.

## Цели обучения

- Распознавание антипаттернов в JavaScript-коде
- Классификация антипаттернов по категориям
- Оценка влияния антипаттернов на качество кода
- Разработка стратегий рефакторинга
- Применение паттернов проектирования для улучшения кода
- Работа с устаревшим (legacy) кодом
- Создание модульной архитектуры приложения
- Устранение глобального загрязнения пространства имен

## Задания

### Task 1 — Anti-Pattern Analysis

**Директория:** `task_1/`

Анализ проблемного JavaScript-кода с идентификацией антипаттернов, их классификацией и оценкой влияния на качество и поддерживаемость кода.

#### Компоненты задания:

**anti_patterns_identified.md**
- Детальная идентификация всех найденных антипаттернов
- Указание конкретных строк кода с проблемами
- Описание каждого антипаттерна
- Объяснение негативного влияния на код

**anti_patterns_classification.md**
- Классификация антипаттернов по категориям
- Группировка похожих проблем
- Приоритизация по степени критичности
- Рекомендации по устранению

**impact_assessment.md**
- Оценка влияния антипаттернов на проект
- Анализ последствий для поддерживаемости
- Оценка технического долга
- Метрики качества кода

#### Основные найденные антипаттерны:

**1. Global Namespace Pollution**
- Загрязнение глобального пространства имен
- Множественные глобальные переменные
- Риск конфликтов имен
- Снижение предсказуемости кода

**2. Code Duplication**
- Дублирование логики валидации
- Повторение кода форматирования
- Нарушение принципа DRY
- Усложнение поддержки

**3. Tight Coupling**
- Жесткая связь между компонентами
- Смешивание бизнес-логики и UI
- Затрудненное тестирование
- Низкая переиспользуемость

**4. Magic Numbers & Strings**
- Хардкод значений в коде
- Отсутствие констант
- Снижение читаемости
- Сложность конфигурирования

### Task 2 — Code Refactoring

**Директория:** `task_2/`

Практический рефакторинг устаревшего кода интернет-магазина с применением паттернов проектирования для создания современной модульной архитектуры.

#### Компоненты задания:

**legacy_code.js**
- Исходный проблемный код (Implementation B)
- Пример legacy-кода с множественными антипаттернами
- Базис для анализа и рефакторинга

**refactoring_plan.md**
- Детальный план рефакторинга
- Анализ проблем текущей реализации
- Стратегия улучшения кода
- Описание применяемых паттернов
- Проектируемая архитектура модулей

**refactoring_documentation.md**
- Полная документация процесса рефакторинга
- Детальное описание каждого модуля
- Обоснование архитектурных решений
- Примеры использования новой структуры
- Сравнение до/после рефакторинга

**refactored_modules/**
- `namespace.js` — Базовое пространство имен приложения
- `module1.js` — Модуль конфигурации (Config)
- `module2.js` — Модуль утилит (Utils)
- `module3.js` — Модуль бизнес-логики (Cart/Core)
- `main.js` — Главный файл инициализации

#### Применяемые паттерны:

**1. Namespace Pattern**
- Единое глобальное пространство имен `MyApp`
- Вложенные пространства имен (`MyApp.Modules`, `MyApp.Utils`)
- Предотвращение загрязнения глобальной области
- Организованная структура кода

**2. Module Pattern (IIFE)**
- Использование самовызывающихся функций
- Создание приватных областей видимости
- Инкапсуляция данных и методов
- Публичное API для взаимодействия

**3. Revealing Module Pattern**
- Явное определение публичного интерфейса
- Скрытие приватной реализации
- Улучшенная читаемость кода
- Четкое разделение ответственности

#### Ключевые улучшения:

**Архитектура:**
- Разделение на логические модули
- Четкая структура зависимостей
- Слабая связанность компонентов
- Высокая когезия внутри модулей

**Качество кода:**
- Устранение глобальных переменных
- Единое место для конфигурации
- Переиспользуемые утилиты
- Защищенное состояние приложения

**Поддерживаемость:**
- Легкость внесения изменений
- Простота тестирования модулей
- Улучшенная читаемость
- Документированный API

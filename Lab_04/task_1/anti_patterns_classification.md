# Antipattern Classification and Solutions

### 1. Global Namespace Pollution
* Classification; Это классическое плохое решение, которое приводит к загрязнению глобального пространства имен. В больших проектах это вызывает конфликты имен и затрудняет отладку.
* How to fix: необходимо сгруппировать все переменные в один глобльный обьект, чтобы минимизировать количество идентификаторов в глобальном контексте.
* Proposed Pattern: `Namespace Pattern(Ch. 11)`
* Reference: Вместо 10 переменных в window, создается один объект:

`const MyApp = { config: {}, utils: {} };`


### 2. Code Duplication: Validation logic
* Classification: Нарушение принципа `DRY` (Don't Repeat Yourself). Повторение одного и того же кода для валидации данных в нескольких местах.
* How to fix: Вынести повторяющуюся логику в отдельный модуль утилит, который будет предоставлять одну универсальную функцию для всех частей приложения.
* Proposed Pattern: `Module Pattern(Ch. 7)`
* Reference: Создание модуля `ValidationModule`, который инкапсулирует логику внутри IIFE и возвращает только нужные методы.

### 3. Configuration Scattered Throughout Code
* Classification: "Жесткое кодирование" настроек и их разбросанность. Это делает приложение негибким при смене окружения (например, при переходе с тестового сервера на рабочий).
* How to Fix: Собрать все константы и настройки в единый объект конфигурации или отдельный модуль, к которому другие части системы будут обращаться за данными.
* Proposed Pattern: `Namespace Pattern (Ch. 11)` / `Object Literal`.
* Reference: Использование структуры `MyApp.Config = { ... };` для централизованного управления параметрами.

### 4. Event Handlers as Global Functions
* Classification: Глобальные обработчики событий трудно поддерживать, и они открывают доступ к логике взаимодействия извне. Это нарушает принцип инкапсуляции.
* How to Fix: Скрыть обработчики событий внутри UI-модуля. Глобально должна быть доступна только инициализация, а сама логика кликов должна быть защищена областью видимости модуля.
* Proposed Pattern: `Module Pattern (Ch. 7)`.
* Reference: Использование немедленно вызываемых функций (IIFE) для создания приватной области видимости для функций `onLoginClick` и других.

### 5. Data Processing with Tight Coupling
* Classification: Функция-«комбайн», которая делает слишком много. Это создает «хрупкий» код: изменение в логике сохранения (cache) может невольно сломать логику валидации.
* How to Fix: Разделить ответственность. Один модуль должен отвечать за хранение (Storage), другой за валидацию (Validation), третий за интерфейс (UI). Функция управления должна лишь координировать вызовы методов этих модулей.
* Proposed Pattern: `Module Pattern (Ch. 7)`.
* Reference: Применение принципа разделения ответственности `   (Separation of Concerns)` через создание независимых модулей для ядра системы.
